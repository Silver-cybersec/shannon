## 2. 架构与信任边界

结论：一次扫描把主机上的 CLI、无认证的 Temporal，以及一个能跑 bash 的 worker 连在一起。密钥和不受信任的目标材料进入同一个容器。编辑器插件把同一套 CLI 交到主机上的另一个代理手里，安全约束写在提示词里。

组件与已读路径：

- **CLI（宿主机）**：解析参数、加载凭据、拉起 compose、`docker run` worker。入口 `apps/cli/src/index.ts`，编排 `apps/cli/src/docker.ts`。
- **Temporal**：`docker-compose.yml:7-12` 使用 `temporalio/temporal:1.7.0` 的 `server start-dev --ip 0.0.0.0`。端口只发布到 `127.0.0.1:7233` 与 `127.0.0.1:8233`。清单里没有认证参数。
- **Worker 容器**：pi 代理执行五类分析与条件利用，可选 Capella 子流程做静态分析。渗透代理工具集含 `bash`（`apps/worker/src/ai/pi/pi-executor.ts:60`）。Capella 明确禁止 bash、写文件和网络工具（`apps/worker/src/ai/pi/capella-agent-executor.ts:54-73`）。
- **插件**：`plugins/shannon/skills/shannon/SKILL.md` 指导编码代理执行 `npx -y @keygraph/shannon@latest`。

数据与权限：

- 供应商密钥来自环境变量或 `~/.shannon/config.toml`（写入模式 `0o600`，`apps/cli/src/config/writer.ts:22-29`）。容器只收到选中供应商的变量名（`apps/cli/src/env.ts:96-112`），值由 Docker 从 CLI 进程环境继承。worker 把 API 密钥放在内存 `RuntimeCredentialStore`（`apps/worker/src/ai/models.ts:163-194`）。`SHANNON_USE_PI_AUTH=1` 时改为可写挂载宿主 `auth.json`。
- 目标账号口令在 `buildLoginInstructions` 里写入送给模型的提示词（`apps/worker/src/services/prompt-manager.ts:174-222`）。函数注释写明口令不另写文件。浏览器会话写入工作区 `auth-state.json`，流程正常结束时删除（`apps/worker/src/temporal/activities.ts:2132-2140`）。
- 目标仓库 `:ro` 挂载。工作区、报告输出、`.shannon` 与 `.playwright` 覆盖层可写。git worktree 另把主仓库的 git 公共目录只读挂进容器（`apps/cli/src/git-worktree.ts:42-70`，提交 `543c5324`）。
- 模型目录在扫描开始时允许联网刷新（`apps/worker/src/ai/models.ts:243`）。错误提示指向 `https://pi.dev/models`。刷新请求的主机和是否携带密钥在 pi SDK 内，本单未安装依赖，**未核实**。
- OpenAI 的 Daybreak 预检把 bearer 令牌发到 `selection.model.baseUrl`（`apps/worker/src/temporal/activities.ts:914`，`apps/worker/src/services/cyber-access-verification.ts:248-280`）。`SHANNON_AI_BASE_URL` 会改变这个地址，这是操作者配置的网关，不是写死的隐蔽回调。`https://staging.keygraph.io` 只出现在预检提示词文本中（同文件第 40 行），这段函数没有请求它。
- 源码检索没有遥测 SDK，也没有 `docker.sock` 挂载。

已读到的绕过或误用点（不是宣称对照全表）：

- URL 只限制协议（`apps/cli/src/index.ts:229-238`），随后在入口脚本里被 shell 重新解析。见 SHANNON-H1。
- 工作区名有白名单（`apps/cli/src/commands/start.ts:307-308`）。自动生成的名字会清洗主机名。仓库目录名没有同样的清洗。
- 元数据地址拦截只覆盖预检时的目标解析。见 SHANNON-M1。
- 路径拒绝规则默认不加载；加载后默认仍是 `*` allow，再叠加 avoid（`apps/worker/src/ai/pi/permission-system.ts:79-83`，`pi-executor.ts:86`）。
- 认证成功只要求 `cookies` 与 `origins` 是数组（`validate-authentication.ts:240-252`）。见 SHANNON-L3。
- 插件里的授权确认、禁止生产目标、禁止回显密钥，都是技能正文，CLI 没有对应强制。见 SHANNON-M4。

## 3. 代码安全

结论：没有在本树里发现故意留下的可利用应用或隐蔽外联。对部署者的高风险有两条：入口命令注入，以及密钥与无 seccomp 限制的 bash 代理共处一室。其余为预检缺口、依赖漏洞和加固不足。

### 故意漏洞与产品功能

- 仓内没有靶场应用。`sample-reports/` 是对第三方应用的历史报告文本，`benchmark/` 是既有报告文件。
- `--exp-php2shell` 是对操作者指定 URL 的崩溃探测，源码写明只做 CVE-2026-109618 的崩溃步骤、不发送 CVE-2026-109619 的后续代码执行请求（`apps/cli/src/exp-php2shell/probe.ts:1-7`）。这是进攻性产品功能。`--yes` 可跳过确认，流量从宿主机发出，不走 worker 的元数据拦截。级别低，见 SHANNON-L1。本单没有发送该探测，也没有验证它在运行时是否停在崩溃步骤。

### 对部署者与宿主机

| ID | 级别 | 结论 |
|---|---|---|
| SHANNON-H1 | 高 | `entrypoint.sh:18` 把 URL 和路径重新送进 shell。已用本机 bash 复核引号语义，未启动产品。 |
| SHANNON-H2 | 高 | `seccomp=unconfined`、同网无认证 Temporal、密钥与可写的 pi 凭据、默认 hosts 转发、渗透代理的 bash。代码已确认；逃逸未动态验证。 |
| SHANNON-M1 | 中 | 元数据拦截只有预检时的 IPv4 `169.254.0.0/16`。 |
| SHANNON-L2 | 低 | 预检 HTTPS 关闭证书校验（`preflight.ts:403-416`）。 |
| SHANNON-L3 | 低 | 空的 cookies 数组可通过认证预检；会话文件在正常结束时删除。 |
| SHANNON-L4 | 低 | `safe.directory *` 与 `/app` 模式 777。 |
